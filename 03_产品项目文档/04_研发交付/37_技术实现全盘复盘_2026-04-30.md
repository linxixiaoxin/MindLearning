## 1. 复盘结论

`book-kb-multi` 当前已经不是单纯“书籍展示页”，而是一个静态内容驱动的多书知识站，并叠加了第一个交互产品实验：思想伙伴选配器。

系统最强的地方是：内容资产已经进入统一入口，前端不依赖后端数据库即可完成多书首页、单书地图、知识图谱、阅读器、专题页、工具页和半自动 AI/Codex 链路。当前构建通过，说明它具备继续演进的工程基础。

系统最脆弱的地方是：内容生成层没有真正产品化，`public/books` 已经积累大量手工/半自动产物，但 `scripts/` 里只有发布同步脚本，没有 `build_registry.py`、`build_book.py`、`build_all.py` 等 README 中设想的核心生成脚本。前端方面，若继续增长，最大风险会集中在巨型组件、自动测试缺口、schema 校验缺失、视觉系统碎片化和图谱体验上。Markdown 渲染已完成基础安全止血，但仍建议补恶意样例测试。

## 2. 当前技术栈

| 层级        | 当前实现                                        | 主要文件                                                | 判断                        |
| --------- | ------------------------------------------- | --------------------------------------------------- | ------------------------- |
| 应用框架      | Vue 3 + Vite                                | `web/src/main.js`、`web/src/App.vue`                 | 适合继续保留，不建议立刻重构到新框架        |
| 路由        | 自研路径解析 + History API                        | `web/src/lib/routes.js`、`web/src/App.vue`           | 当前可用，但路由增长后应评估 Vue Router |
| 内容加载      | 静态 JSON + Markdown fetch                    | `web/src/lib/bookData.js`、`web/public/**`           | 简洁，但缺少 schema 校验和生成流水线    |
| 搜索        | 前端内存索引                                      | `web/src/lib/searchIndex.js`、`App.vue`              | 小规模可用，大规模需懒加载和索引预构建       |
| 图谱        | D3 force simulation                         | `KnowledgeGraph.vue`                                | 可自定义强，但需要稳定布局、标签避让和性能策略   |
| Markdown  | `marked` + DOMPurify + `v-html`             | `ArticleReader.vue`                                 | 已完成安全止血，后续补恶意样例测试        |
| 工具产品      | 前端规则匹配                                      | `ThoughtPartnerTool.vue`、`thoughtPartnerData.js`    | MVP 可解释，但组件过重，需要抽引擎       |
| 图片导出      | 自绘 Canvas                                   | `ThoughtPartnerTool.vue`、`ArticleReader.vue`        | 好处是可控，坏处是视觉和页面双实现         |

| AI 接口     | Netlify Function + OpenAI Responses API     | `web/netlify/functions/thought-partner-insight.mjs` | 结构化输出方向正确，需模型/错误/日志策略     |
| 发布        | RedBook 源仓库 -> MindLearning 发布仓库 -> Netlify | `scripts/sync_publish_repo.ps1`、`DEPLOY.md`         | 隔离思路正确，但同步排除规则和发布检查还需自动化  |

## 4. 前端运行链路

### 4.1 应用启动

```text
index.html
-> /src/main.js
-> App.vue
-> loadRegistry()
-> 根据 URL 解析当前 view
```

`App.vue` 承担应用外壳、顶部导航、搜索、路由加载、书籍/专题/工具视图切换、阅读器打开关闭等职责。此前已抽出 `routes.js` 和 `searchIndex.js`，但 `App.vue` 仍有约 1089 行，继续增长后会再次变成中心化协调器。

### 4.2 路由模型

当前支持的路径：

| 路径 | view | 数据来源 |
| --- | --- | --- |
| `/` / `/books` | `library` | `registry/books.json` |
| `/books/:slug` | `home` | `public/books/:slug/*.json` |
| `/books/:slug/graph` | `graph` | `graph.json` |
| `/books/:slug/note/:nodeId` | `reader` | `file-map.json` + Markdown |
| `/topics/:slug` | `topic` | `topics/:slug/topic.json` |
| `/tools/thought-partner` | `thoughtPartner` | `thoughtPartnerData.js` |
| `/tools/thought-partner/thinkers/:id` | `thinkerProfile` | `thoughtPartnerData.js` |
| `/tools/mindset-trap-diagnostic` | `mindsetTrapDiagnostic` | 组件内数据 |
| `/tools/leadership-mindset-assessment` | `leadershipMindsetAssessment` | 组件内数据 |

短期继续使用自研路由可接受。中期如果新增参数、嵌套路由、页面 meta、路由守卫、懒加载 chunk，就应该引入 Vue Router。

### 4.3 数据加载

`bookData.js` 的职责：

```text
loadRegistry()
  -> /registry/books.json

loadBookBundle(slug)
  -> /books/:slug/site.json
  -> /books/:slug/graph.json
  -> /books/:slug/file-map.json
  -> /books/:slug/toc.json
  -> /books/:slug/home-sections.json
  -> /books/:slug/alias-map.json

loadTopicBundle(slug)
  -> /topics/:slug/topic.json
```

优点：

- 静态部署友好。
- 前端 bundle 不直接包含全部书籍内容。
- 每本书独立产物，局部缺失时容易定位。

问题：

- 没有 schema 校验，字段错误只会在运行时暴露。
- 缓存是内存级 Map，没有版本刷新策略。
- 多个 JSON 之间的引用一致性靠人工维护。
- `configs/books/*.book.json` 和 `web/public/registry/books.json` 之间存在重复信息，当前没有自动同步。

## 5. 多书站内容资产链路

理想链路应是：

```text
01_sources / 03_outputs / 06_index
-> configs/books/*.book.json
-> scripts/build_book.*
-> web/public/books/:slug/*
-> scripts/build_registry.*
-> web/public/registry/books.json
-> Vue 前端加载
```

当前实际链路更像：

```text
本地内容资产
-> 半自动或人工生成 public/books
-> 手工维护 registry
-> 前端加载
```

这意味着后续每扩一本书，都可能重复出现：

- `site.json`、`graph.json`、`file-map.json`、`toc.json` 字段不一致。
- `graph.links` 指向不存在节点。
- `registry` 书籍状态与 public 目录不一致。
- 首页 stats、coverImage、entryTopics 过期。
- Markdown 文件名与 nodeId / aliasMap 对不上。

### 6.1 书库首页

`BookLibrary.vue` 已经从单列书卡升级为：

- 当前接入统计。
- 分类筛选。
- 主推书。
- 重点书。
- 紧凑书架。
- 产品实验和专题继续探索区。

展示规则已部分抽到 `libraryDisplay.js`，这是正确方向。下一步应该把“主推书选择”和“筛选规则”改成数据驱动，不要把 `mindset-traps` 这类特殊加分长期写死在前端。

### 6.2 单书首页

`HomeView.vue` 负责：

- 单书 hero。
- 推荐阅读路径。
- 章节 journey map。
- stats。
- section card。
- follow / community 抽屉。

它视觉完成度较高，但仍是强内容页组件，要求 `site.json` 字段齐全。缺失字段时会出现空按钮或空文案风险，需 schema 和默认值。

### 6.3 知识图谱

`KnowledgeGraph.vue` 使用 D3 force simulation，并提供：

- zoom / pan。
- 节点拖拽。
- 类型筛选。
- tooltip。
- 详情面板。
- 关联节点列表。
- activeNode 聚焦。

实现上已经注意到坏边过滤，这是必要的。D3 官方文档明确说明 force simulation 会修改传入节点对象，link force 也可能把 `source/target` 从字符串替换为对象，因此当前复制节点、过滤 links 的做法是对的。后续如果图谱需要保存布局，应将布局坐标单独持久化，避免把运行时变异误写回源数据。

### 6.4 阅读器

`ArticleReader.vue` 负责：

- 按 nodeId 从 `FILE_MAP` 找 Markdown。
- fetch Markdown。
- 正则解析 frontmatter。
- 转换 `[[wiki-link]]`。
- 将 Markdown 转 HTML。
- 通过 `v-html` 注入页面。
- 可选显示图片或 canvas 结构画。

历史最大技术风险在这里，已于 DEV-016 完成止血：

- `marked` 官方文档提示它不会净化输出 HTML，处理不可信内容时要用 DOMPurify 等工具。
- 本项目原先使用 `v-html` 直接渲染 `marked.parse` 结果，虽然内容来自本地仓库，但内容生产链路里有 AI、外部文本和批量迁移，不能把它当成永远可信。
- 当前实现已在 `ArticleReader.vue` 接入 DOMPurify，对 Markdown 渲染后的 HTML 做净化。
- `marked` 已升级到 `18.0.2`，`postcss` 已升级到 `8.5.12`，`npm audit --omit=dev` 返回 0 vulnerabilities。

### 6.5 专题页

## 7. AI 与 Codex 链路

### 7.1 Netlify Function

`thought-partner-insight.mjs` 使用 OpenAI Responses API 和 `json_schema` 结构化输出，方向正确。OpenAI 官方文档说明结构化输出能让模型结果匹配 JSON Schema；模型页显示 `gpt-4.1-mini` 支持 Responses 和 Structured outputs，但同页也提示复杂任务建议从 GPT-5 mini 起步。

当前建议：

- 保留 `OPENAI_MODEL` 环境变量。
- 默认模型不要写死在业务函数里，应进入配置和 ADR。
- 加入超时控制、请求日志摘要和错误码分类。
- 前端 fallback 保持。
- 不在错误信息里暴露 key、prompt 或完整 payload。

### 7.2 本地 Codex bridge

`codex-insight-bridge.mjs` 监听 `127.0.0.1:8787`，支持：

- `GET /status`
- `POST /thought-partner/inbox`
- `GET /thought-partner/response`
- `POST /thought-partner/response`

定位应该保持为“内部研发协作工具”，不要包装成普通用户能力。原因：

- 端口硬编码在前端。
- CORS 允许所有来源。
- 没有鉴权。
- response 文件只有最新一份，没有 request id 池。
- 页面轮询 60 次，每次 2 秒，适合调试，不适合产品化。

## 9. 100+ 本扩容专项判断

如果准备把本地 100 多本书全部推上网站，项目会从“多书实验站”变成“内容发布平台”。真正的风险不是前端页面数量，而是内容生产、校验、搜索、发布、版权和视觉质量门禁。

### 9.1 会面临的问题

| 问题 | 影响 | 当前状态 |
| --- | --- | --- |
| 手工维护会失控 | `configs/books`、`registry/books.json`、`public/books` 多处同步，100 本后很容易漂移 | 已开始补校验脚本 |
| 内容构建层缺失 | 扩书依赖人工经验，无法稳定批量生产 | 仍需 `build_book/build_registry/build_all` |
| 全站搜索会变慢 | 前端运行时逐本加载会拖慢首屏和搜索 | 需要预构建轻量搜索索引 |
| 图谱不能全量合并 | 100 本所有节点放进一个图会不可读 | 应保留单书图谱、专题图谱、概念索引 |
| 发布门禁不足 | 坏边、缺文件、占位 SEO、依赖漏洞可能带病上线 | 已完成第一版 `validate:site` |
| 公开内容边界 | 原文、摘录、翻译、AI 改写的公开边界需要规则 | 需要单独版权/公开改写规范 |
| 书库首页信息架构 | 100 张书卡平铺不可用 | 需要分类、作者、主题、问题、系列多入口 |

### 9.2 建议架构

100+ 本扩容后，推荐链路应调整为：

```text
01_sources / 03_outputs / 06_index
        ↓
configs/books/*.book.json
        ↓
scripts/build_book
        ↓
web/public/books/<slug>/
        ↓
scripts/build_registry + build_search_index + validate_site
        ↓
web/public/registry/books.json
web/public/search/search-index.json
web/public/sitemap.xml
        ↓
Vue/Vite 前端按需加载
```

前端层短期可以继续保留 Vue/Vite。架构升级重点不是换框架，而是补三层能力：

1. 内容构建：把书籍配置、源资产和 public bundle 的生成自动化。
2. 质量门禁：把 registry、图谱、file-map、图片路径、SEO 占位和依赖审计自动化。
3. 按需加载：全站只加载轻量 registry/search index，进入单书后再加载完整 bundle。
