## 1. 一句话判断

这个产品不应只是“本地知识库的可视化网页”，也不应只是“接一个 AI 聊天框”。

更准确的定位是：

```text
一个把真实人生问题转成可拆解、可学习、可行动、可沉淀、可发布内容的个人思想工作流系统。
```

其中：

- 本地知识库是底层资料库和证据库。
- 网页是工作流界面，负责把问题推进成结构化过程。
- AI 是流程中的思想伙伴、教练、证据检索员和内容转译员。
- 小红书和公众号内容不是另一个孤立模块，而是问题解决过程的自然副产品。

## 2. 核心洞察

用户的每一个真实问题，天然包含一条可以被产品化和内容化的链路：

```text
真实处境
-> 原始表达
-> 卡点命名
-> 隐含假设
-> 情绪和需要
-> 可学习视角
-> 书籍证据和概念
-> 最小行动
-> 复盘反馈
-> 方法沉淀
-> 小红书图文素材
-> 数据反馈
-> 下一轮问题和选题
```

这条链路同时解决三个问题：

1. 产品体验：用户带着问题进来，不必先知道该读哪本书。
2. 学习闭环：每个问题都会沉淀成一个可复用的 Problem Case。
3. 内容增长：每次高质量拆解都可以转译成一篇或一组小红书图文素材。

## 3. 系统角色重新分层

### 3.1 本地知识库

本地知识库不是“展示给用户看的仓库”，而是系统的底层燃料。

它应该承担：

- 书籍、K 卡、N 卡、摘要、视觉钩子、过往内容的数据储存。
- 问题案例和思想伙伴可以调用的证据池。
- 已发布内容和表现数据的历史记录。
- 方法模板、表达模板、工作流模板的版本库。

### 3.2 网页工作流

网页不是静态站点，而是一个可操作的工作台。

它应该承担：

- 接住用户的真实输入。
- 让问题被一步步拆开，而不是直接给答案。
- 提供可切换的工作流模式，比如教练、一对一、圆桌、辩论、私董会。
- 把每一步输出沉淀成卡片、素材和任务。
- 让用户不用在浏览器、IDE、Codex、表格之间来回切。

### 3.3 AI 协作层

AI 不应被设计成单一聊天机器人，而应被设计成多个“可调用角色”和“可编排步骤”。

第一阶段可以先假装是多角色，由一个模型按角色规则输出。

中期再升级为真正的多智能体编排：

- 主持人 agent：控制流程，不急着给结论。
- 教练 agent：负责提问、澄清、行动承诺。
- 证据 agent：从本地知识库找书籍、概念和卡片。
- 反方 agent：指出盲点、隐含假设和可能的自我欺骗。
- 内容编辑 agent：把过程转译成小红书图文素材。
- 运营 agent：对照已发布数据，判断选题优先级。

## 4. 新核心对象模型

### 4.1 Life Problem

前端真实输入，不要求一开始就结构化。

```js
{
  id: 'life-problem-xxx',
  rawText: '我发现自己一跟别人解释就很着急，好像必须证明我是对的',
  scene: '亲密关系 / 工作沟通 / 自我表达',
  emotionWords: ['着急', '委屈', '害怕被误解'],
  createdAt: '2026-05-02'
}
```

### 4.2 Problem Case

被命名和拆解后的问题案例。

```js
{
  id: 'need-to-prove-right',
  title: '为什么我一解释就像在打仗',
  problemNaming: '这不是表达能力差，而是把被理解和自我价值绑定在一起',
  hiddenAssumptions: [
    '如果对方不认同我，就说明我不够好',
    '解释清楚就能换来安全感',
    '对话必须赢，否则我就是输的一方'
  ],
  needs: ['被理解', '安全感', '自我边界'],
  perspectivesToLearn: ['非暴力沟通', '阿德勒', '戈夫曼', '观看方式'],
  evidenceNodes: ['非暴力沟通 N 卡', '日常生活中的自我呈现 N 卡'],
  minimumAction: '把“你根本没听懂”改成“我想确认一下我刚才表达的重点有没有传过去”'
}
```

### 4.3 Roundtable Session

一次圆桌协作记录。

```js
{
  id: 'roundtable-session-xxx',
  problemCaseId: 'need-to-prove-right',
  mode: 'yes-and-relay',
  participants: ['火把教练', '关系翻译者', '反方朋友', '证据馆员', '内容编辑'],
  turns: [],
  output: {
    clarifiedProblem: '',
    hiddenAssumptions: [],
    newPerspectives: [],
    actionCard: '',
    xhsSeed: ''
  }
}
```

### 4.4 Content Artifact

问题拆解过程回流成内容素材。

```js
{
  id: 'content-artifact-xxx',
  sourceProblemCaseId: 'need-to-prove-right',
  format: 'xiaohongshu-carousel',
  hook: '为什么你一解释，就像在和对方打仗？',
  slides: [],
  evidence: [],
  status: 'draft'
}
```

## 5. 圆桌思想伙伴的产品形态

用户提出的“真的有一张画面，几个人围坐在一起”非常值得做。

它的价值不是装饰，而是让用户直观看见：

```text
我不是在和一个 AI 聊天，
我是把问题放到一张桌子上，
让不同视角围绕它工作。
```

### 5.1 圆桌基础界面

第一屏可以是一个工作台：

- 中间：用户的问题卡。
- 周围：3 到 6 个思想伙伴头像或席位。
- 右侧：当前工作流规则。
- 下方：对话流、证据流、行动卡、内容素材四个 tab。

视觉上不需要做复杂 3D，第一版用俯视圆桌、头像席位、发言高亮就足够。

### 5.2 三种互动呈现

#### 形态 A：圆桌剧场

适合强调“多个思想伙伴正在协作”。

界面：

- 圆桌席位亮起。
- 当前发言者高亮。
- 中间问题卡逐步被贴上标签。
- 每轮结束生成一张“阶段卡”。

适合模式：

- Yes-and 接力提问
- 多视角辩论
- 私董会
- 世界咖啡

#### 形态 B：仿微信聊天

适合日常低摩擦使用。

界面：

- 像微信群一样，不同思想伙伴一条条发言。
- 用户可以点“追问这个人”“让反方说一句”“生成行动卡”。
- 聊天流旁边同步生成结构化卡片。

适合模式：

- 快速脑暴
- 灵感整理
- 内容转译
- 多角色对话

#### 形态 C：一对一教练

适合私密、敏感、需要慢慢澄清的问题。

界面：

- 一个教练角色，少量追问。
- 一次只问一个问题。
- 不急着生成选题或结论。
- 最终输出“我现在真正卡住的是...”和“今天一个小动作”。

适合模式：

- 火把教练
- 教练技术
- 情绪和需要澄清
- 隐含假设识别

## 6. 内置工作流规则

### 6.1 火把教练 Yes-and 接力

规则：

- 每个角色只能接住上一个角色的一点继续推进。
- 不允许一开始就批判用户。
- 每轮只增加一个更亮的看见。
- 最后必须落到一个最小行动。

输出：

```text
你真正说出的不是“我不知道怎么办”，
而是“我还没有找到一个不伤害自己的表达方式”。
```

### 6.2 隐含假设拆解

规则：

- 先复述用户原话。
- 找出其中可能的“必须”“应该”“如果不...就...”。
- 每个假设给一个替代表达。
- 不直接否定用户，而是提供可检验版本。

输出：

```text
原假设：如果我没有马上回应，对方就会觉得我不在乎。
替代假设：关系里的在乎不只通过即时回应证明，也可以通过稳定解释和后续行动证明。
```

### 6.3 多视角辩论

规则：

- 正方说“这个问题为什么成立”。
- 反方说“这个问题可能哪里想错了”。
- 证据方给书籍和概念。
- 主持人收束成新的问题命名。

适合：

- 决策困境
- 职业选择
- 关系冲突
- 内容定位摇摆

### 6.4 内容转译工作流

规则：

- 不直接把心理过程发成流水账。
- 先提取“读者熟悉的表层场景”。
- 再提取“让人停下来的反常识命名”。
- 再给出“3 到 5 页图文逻辑链”。
- 最后绑定一张书籍证据卡或方法卡。

输出结构：

```text
选题标题
-> 封面钩子
-> 读者场景
-> 误区命名
-> 底层机制
-> 书籍视角
-> 一句可尝试表达
```

## 7. 多智能体协作怎么做到

多智能体不是一定要同时启动很多模型。更重要的是“角色、状态、输入输出契约、编排规则”。

### 7.1 第一阶段：单模型多角色

一个模型按固定角色脚本输出。

优点：

- 成本低。
- 延迟低。
- 工程简单。
- 更适合先验证界面和工作流。

缺点：

- 角色之间的差异可能不够强。
- 很难真正并行检索和辩论。

适合现在先做。

### 7.2 第二阶段：编排式多 agent

由一个 orchestrator 控制流程，按步骤调用多个角色。

```text
用户问题
-> 路由器判断问题类型
-> 问题命名 agent
-> 证据检索 agent
-> 圆桌发言 agents
-> 主持人收束 agent
-> 内容转译 agent
-> 保存 Problem Case / Content Artifact
```

优点：

- 每个 agent 的职责更清楚。
- 可插入本地知识库检索。
- 可把中间结果持久化，便于复盘和内容生产。

缺点：

- 成本更高。
- 延迟更长。
- 需要更严格的结构化输出。

### 7.3 第三阶段：人机共编排

用户可以在界面上控制流程：

- “让反方再说一句”
- “只看书籍证据”
- “先别生成内容，继续问我”
- “把这轮变成小红书图文”
- “把这个问题沉淀成新 Problem Case”

这会比纯自动化更适合这个项目，因为用户本身也是内容创作者和产品定义者。

## 8. AI API 接入方向

当前本地已经有：

```text
网页 AI 指令入口 -> bridge -> agent daemon -> Codex CLI -> 写回页面
```

这适合本地开发和低频命令执行。

如果要做真正产品化的即时交互，仍然需要接入 AI API。更稳的分层是：

### 8.1 继续保留 Codex CLI

用途：

- 本地改代码。
- 本地读文件和跑脚本。
- 处理需要操作仓库的任务。

### 8.2 新增 API 层

用途：

- 页面内即时提问。
- 圆桌对话。
- 选题拆解。
- 小红书素材生成。
- 结构化保存会话。

推荐技术形态：

```text
web 页面
-> 本地/Netlify Function API
-> AI provider
-> structured JSON
-> 保存 session / artifact
-> 页面刷新结果
```

### 8.3 模型选择建议

需要以“任务分层”选择模型，而不是所有事情都上最强模型。

| 任务 | 推荐模型层级 | 原因 |
| --- | --- | --- |
| 标签分类、路由、去重、简单摘要 | 轻量 / nano 模型 | 高频、便宜、延迟低 |
| 普通选题、圆桌发言、教练追问、小红书草稿 | mini 模型 | 性价比主力，质量足够 |
| 深度系统化、复杂思想综合、长文档重构 | 主力大模型 | 需要更强推理和结构感 |
| 重要发布稿、复杂产品判断、模型仲裁 | 高阶模型 | 低频使用，保证质量 |

如果优先接 OpenAI API，可以先看这几类官方能力：

- Responses API：适合统一文本生成、工具调用和结构化输出。
- Agents SDK：适合未来做多 agent、handoff、工具调用和流程编排。
- File Search / Vector Store：适合把本地书籍卡片和内容资料变成可检索证据层。
- Model pricing：用于按任务分层控制成本。

### 8.4 成本控制原则

- 先本地检索，再把少量证据喂给模型。
- 先用轻量模型做路由和标签。
- 圆桌不要一口气让 6 个角色长篇发言，每轮每人限制 1 到 3 句话。
- 生成内容时先生成结构，再按需展开。
- 对常用工作流做 prompt 模板和缓存。
- 对“读取大量书籍上下文”的任务，避免每次把全量资料塞进上下文。

## 9. 小红书工作台 AI 交互的方向

用户的判断是对的：

```text
把常用语句、上下文、工作流按钮内置在小红书工作台，
会比每次切到 Codex 当前窗口更快、更稳、更适合日常运营。
```

原因：

- 页面知道当前选中的主题群、内容数据、今日任务和灵感库。
- 页面可以把上下文自动带给 AI，不需要用户重复复制。
- 常用动作可以按钮化，比如“拆 10 个选题”“生成封面钩子”“绑定书籍证据”。
- 输出可以直接回到内容中台，变成任务、草稿、素材或复盘记录。

### 9.1 建议内置快捷语句

| 场景 | 快捷动作 |
| --- | --- |
| 选题 | 再拆 10 个标题，按痛点强弱排序 |
| 钩子 | 给当前选题写 5 个封面钩子 |
| 图文 | 生成 6 页小红书图文逻辑链 |
| 证据 | 从本地书籍卡片里找 3 个可绑定视角 |
| 数据 | 对照历史数据判断这个选题像哪个已发布内容 |
| 复盘 | 把这条笔记拆成可复用的方法模板 |
| 圆桌 | 让 4 个思想伙伴围绕这个选题辩论一轮 |
| 任务 | 把这条选题加入本周发布计划 |

### 9.2 页面上可做的交互

在 `/tools/content-ops` 里新增一个“AI 操作栏”：

- 当前上下文：主题群、选中内容、数据筛选、今日任务。
- 快捷命令：选题、钩子、图文、证据、复盘、圆桌。
- 输出位置：回复、草稿、任务、素材库。
- 执行器：Codex CLI / API / 手动复制。

## 11. 建议开发路线

### P0：把工作流讲清楚

- 完成本文档。
- 在内容中台 AI 指令入口增加快捷命令和上下文说明。
- 设计圆桌页面静态样张。
- 先用固定数据模拟一次“问题 -> 圆桌 -> 内容种子”。

### P1：单模型多角色

- 新增 `roundtableModeData.js`。
- 新增 `roundtableAgentData.js`。
- 新增 `/tools/roundtable` 页面。
- 先不接 API，或只接 Codex CLI / 本地 API 生成 JSON。

### P2：接 AI API

- 新增本地或 Netlify Function。
- 支持结构化输出。
- 支持把 session 写到 `codex-inbox` 或本地 JSON。
- 让内容中台可以直接读取生成结果。

### P3：知识库检索接入

- 给 Problem Case 绑定 K/N 卡和书籍证据。
- 先做轻量关键词检索。
- 再考虑向量检索和 File Search。

### P4：内容自动化闭环

- 从圆桌结果生成小红书图文素材。
- 写入内容中台草稿区。
- 绑定发布计划。
- 记录发布后数据。
- 用数据反推下一轮选题。

## 12. 暂时不做

| 不做 | 原因 |
| --- | --- |
| 一开始就全自动多智能体 | 工程复杂，且可能掩盖真正要验证的工作流 |
| 一开始就开放无限聊天 | 容易变成泛聊天工具，失去问题拆解和内容回流主线 |
| 一开始就自动发布小红书 | 平台风险和内容质量风险高 |
| 一开始就做复杂 3D 圆桌 | 第一版重点是流程和角色协作，不是视觉炫技 |
| 对心理问题做诊断式回答 | 产品定位应是思考、学习和表达辅助，不是医疗或心理诊断 |

## 13. 当前最小可验证版本

最小版本可以是：

```text
用户输入一个问题
-> 选择圆桌模式
-> 系统生成 4 个角色的一轮发言
-> 主持人收束成隐含假设、学习视角、最小行动
-> 一键生成小红书 6 页图文大纲
-> 存入内容中台灵感库
```

这已经能验证最关键的假设：

- 用户是否愿意从真实问题进入？
- 圆桌形式是否比单一聊天更有启发？
- 问题拆解是否能稳定转成内容素材？
- 内容中台是否真的减少上下文切换？

## 15. 这条路线的产品判断

这套想法是成立的，而且比“做一个知识库网站”更有生命力。

它的核心优势是：

```text
用户的问题就是产品入口，
用户的思考过程就是学习过程，
学习过程的结构化沉淀就是知识资产，
知识资产的表达转译就是内容素材，
内容数据的反馈又会反过来训练下一轮问题拆解。
```

最需要守住的是边界：

- 不做泛聊天。
- 不做纯资料展示。
- 不把多智能体做成空泛表演。
- 不让内容生产压倒真实问题解决。

下一步最好做一个 `/tools/roundtable` 的静态可交互样张，让这套系统从概念变成可以触摸的界面。

本轮已经把“圆桌智能体与内容回流系统”先做成一个前端可交互原型。

- 顶部导航新增“圆桌”入口。
- 工具库 registry 新增“圆桌工作流”。
- 新增静态数据层 `web/src/data/roundtableData.js`。
- 新增页面组件 `web/src/components/RoundtableStudio.vue`。

第一版交互闭环：

```text
选择 / 生成模拟用户
-> 用户带着一个真实问题进入
-> 圆桌展示主持人、火把教练、证据馆员、反方朋友、内容编辑
-> 切换 Yes-and、辩论、一对一教练、内容转译
-> 推进问题进入、卡点命名、假设拆解、视角学习、行动承诺、内容回流
-> 用户成长指标发生变化
-> 输出小红书素材雏形
```

虚拟用户能力：

- 预置知识型创作者、新晋团队负责人、高考后选择者三个模拟用户。
- 支持用“书籍生成 / 网站生成 / 内容数据生成”三类来源线索生成一个新的模拟用户。
- 模拟用户拥有状态、触发事件、问题、特质、成长指标和时间线。
- 进入每个阶段后，用户的觉察、行动感、表达、证据感会发生变化。

当前仍是静态 / 规则生成，不接真实模型。

下一步产品化方向：

1. 把圆桌输出保存成 `Roundtable Session`。
2. 把内容素材写入 `/tools/content-ops` 的灵感库或草稿区。
3. 接入 API，让虚拟用户、圆桌发言和内容转译变成动态生成。
4. 给每个圆桌角色绑定可调用的本地书籍证据和 K/N 卡。
5. 增加“真实用户输入问题”入口，而不是只用模拟用户。
